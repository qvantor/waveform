# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Waveform is an experimental browser wavetable synth (TypeScript + Web Audio API, React 18). It is an Nx 14 monorepo with one app (`apps/waveform`) and four libs (`libs/math`, `libs/rxjs-react`, `libs/ui-kit`, `libs/preset-schema`), plus Netlify serverless functions in `netlify/` and a Postgres database for presets. Deployed to Netlify.

## Architecture

### State: `rxModel` (libs/rxjs-react)

All app state and audio logic live in RxJS "models", not React state. The pattern:

```ts
const model = (deps) =>
  rxModel((initial) => ({ $foo: new PrimitiveBS(0), audioNode, ... }))  // state: BehaviorSubjects + Web Audio nodes
    .actions((model) => ({ setFoo: (v) => model.$foo.next(v) }))
    .subscriptions((model, actions) => [ ...rx subscriptions wiring state to audio... ])
    .plugins(urlSnapshotPlugin({ modelToSnap, applySnap }))
    .destroy((model) => { ... });

export const { ModelProvider: FooProvider, useModel: useFoo } = rxModelReact('fooModel', model);
```

- Each builder call returns a new immutable factory; `init` runs actions, subscriptions, and plugin `onInit`; unmount runs `destroy`, unsubscribes, and plugin `onStop`.
- `rxModelReact` wraps a model in a React context. `<FooProvider initial={...} {...deps}>` takes the `initial` value plus dependency props (other models' `[model, actions]` tuples); `useFoo()` returns `[model, actions]`.
- Components read observables via `useBehaviorSubject($x)` / `useObservable`. BehaviorSubject helpers: `PrimitiveBS`, `ArrayBS`, `ObjectBS`. Observable names use a `$` prefix.
- Dependency injection is done through provider nesting, so provider order matters. The tree in `apps/waveform/src/app/synth/index.tsx` defines it: InputController → SynthCore → Envelopes → Lfo (the LFOs: the voices node of the synth core runs them) → Modulation → Oscillator1/2 → MidiController → Filter → Synth (the filter in its voices) → Fx (follows the synth's last note and the LFOs) → SoundSwitch (a preset switch silences them) → KeyboardController → Presets.

### Audio graph (apps/waveform/src/app/synth/common/modules)

- `synth-core.ts` owns the single `AudioContext` and its wavetable oscillator (`wavetables`, `createWavetableEngine`): `voices node → preGain → fxIn → [fx chain] → fxOut → masterGain → masterLimiter → destination` (every note plays in the voices node, the filter is in each voice). `mute(seconds)`/`unmute()` (the sound switch) fade `fxOut.gain` out and step it back to 1, nothing else automates it; the limiter's `clear` (its `fx_clear`) forgets the gain reduction of the sound before. `$masterGain` is linear, the Master knob (`master-handle.tsx`) shows it in dB from −40 (silence) to +12: above 0 dB it drives the limiter. The header analysers tap `output` (the limiter's output).
- The latency of the output (`synth/common/latency/`): the `latencyHint` of the context, chosen at its creation (`resolveLatency` of `latency.ts`), so a change reloads the page (`reloadPage`: the tab keeps the sound and the MIDI input). Only Chromium on a desktop takes the hint (`canChooseLatency`: `navigator.userAgentData`, its brands, not `mobile`; Safari and Firefox ignore it, they get none): low is `0` (128 frames: `baseLatency` 2.67 ms + `outputLatency` 8 ms at 48 kHz on macOS), normal `'interactive'` (256 frames: 5.33 + 16 ms; a hint between them rounds up to 256). The mode (localStorage `latencyMode`: auto, low, normal; where the storage keeps nothing, site data blocked or full, `canKeepLatency`, the latency is normal and the settings offer no choice) is chosen under the Settings key, right of Midi (`settings/settings-button.tsx`; the page reloads, so its select has no ◀ ▶, `arrows` of the ui-kit `Select`); auto starts low and plays normal once it learnt it (localStorage `latencyAuto`; auto chosen again forgets it), only where the browser counts dropouts (`canCountDropouts` of `dropouts.ts`: `AudioPlaybackStats` with `underrunEvents`, the interface, not an instance, and `playbackStats` on `AudioContext.prototype`; Chromium before 146 has none: auto is normal there, nothing would warn of dropouts at low or leave it; a low chosen by hand stays, its note asks to choose normal if the sound crackles). At low the synth core polls the dropouts the browser counts (`playbackStats.underrunEvents`, `dropouts.ts`; Chrome 155 has it, Chromium 133 not: no guard there) once a second, `$dropouts` (the settings show them): `DROPOUT_SECONDS` (3) seconds with new ones within `DROPOUT_WINDOW` (60 s of the clock, `performance.now`: a hidden page polls once a minute) and auto keeps normal from the next start on (those while a preset switch silences the output, `$muted` of the synth core, and within `REPORT_LAG` 2 s after are shown, not counted), `$dropoutWarning` shows a toast that offers normal now (`switchToNormalLatency`: a low chosen by hand becomes normal; once, `dismissDropoutWarning`). The clocks of the context don't show a dropout (`currentTime`, `getOutputTimestamp`), and Chromium 133 grows its FIFO after one (its PushPullFIFO earmark) without telling `outputLatency`: a lateness worked out in a worklet (no `performance` there, `Date.now()` only) is not one.
- The master limiter (`synth/common/limiter/`) is the last stage, after the master volume. Its core (`dsp/limiter`, `limiter-wasm.ts`, the ceiling in `limiter-params.ts`; tested offline: `limiter-dsp.spec.ts`) is a stereo linked brickwall at −0.5 dBTP with a 4× true peak detector (`dsp-core/src/true_peak.rs`, polyphase Kaiser sinc whose phase 0 is the input itself), 2 ms lookahead, the needed gain held for 20 ms (the gain never moves inside a bass wave), a fast (50 ms) and a slow (0.5 s) release envelope (short peaks let go fast, dense parts slowly, no pumping between their notes; once the sound has needed less than the slow one for 250 ms it lets go at the fast rate, down to what the sound still needs) and two moving averages over the lookahead (S-shaped attack). The detector skips the interpolation while the last 32 samples are below the ceiling / `TRUE_PEAK_BOUND` (−8.6 dBFS: no point between them can reach the ceiling), and sums its 3 phases in one pass over the history, so quiet parts cost 0.2% of a core (about 0.6% while limiting; the TS core of before stage 5, the Rust one about half) and the output is the same to the bit. No sample goes over the ceiling, the true peak of band-limited sound stays under 0 dBFS (the 4× grid reads at most cos(π·f/4) low), below the ceiling, once released, the sound passes bit for bit, delayed by `latency` (2.3 ms at 48 kHz). `limiter.worklet.ts` registers the processor, `master-limiter.ts` loads it with `createWorkletFx`; until it is ready (while it loads, after the module or its processor failed) the master is silent (no fallback: the oscillators need the same, AudioWorklet and wasm SIMD), a failed one shows a toast on every screen (`LimiterStatus`, `synth/synth/components/`), its Retry loads it again, with the oscillators if they failed too (`retryAudio` of the synth core).
- The `fx` model (`synth/fx/`) wires the FX rack between `fxIn` and `fxOut`. Effects are defined in `FX_REGISTRY` (`fx/effects/`, params and ranges from `FX_PARAMS` in `libs/preset-schema`). `createFxSlot` wraps each one: `mix` is a crossfade (`mixGains`: 0 only dry, 1 only wet; equal power for delay and reverb, both at −3 dB at 0.5; linear for a core with `linearMix`, the distortion: its wet signal is the dry one reshaped and in time with it, they add up like one sound and equal power would be 3 dB louder in between; the default of a fresh effect is per type, `FX_MIX_PARAMS`: the distortion is all wet, delay and reverb 0.3), bypass passes only the dry signal at full level; a core with `latency` (the distortion) gets its dry signal delayed as much (`dryDelay`), so the timing never jumps and the mix doesn't comb filter. The chain is the added effects in `$order`; adding an effect type means a registry entry plus its preset schema. `clear()` (the sound switch, after the next preset is applied) makes every effect forget its tail at once, in the chain or not (`FxCore.clear`), and sets the gains of its slot (send, dry, wet) at its knobs at once (a mix its routes move follows them): the worklets post `{ clear }` (`fx_clear` of their cores: emptied and idle as once drained, the next sound starts at the params as they are then, no glide from those before; a reverb idle already is empty), the delay makes its lines, bandpasses and pan offsets again (a DelayNode can't be emptied: fed silence it plays its last second) at the values of its knobs at once (`instantly` of `createFxParams`: from the defaults of a node Time would chirp). `FX_TYPES` is the default chain order (distortion, delay, reverb); `normalizeFxOrder` puts a type missing from a saved order (saved before it existed) at its default place, before the first effect that follows it in `FX_TYPES`, not at the end.
- The reverb runs in an AudioWorklet: its core (`dsp/reverb`, `reverb-wasm.ts`, its params in `reverb-params.ts`) is a 16-line FDN (its lines in pairs in the lanes of f64x2: line 2p, which goes left, in the low lane, 2p + 1 in the high one, each lane the operations of its line, the sums in their order; the input stage, the predelay and the diffusers of both channels in the lanes: 125 against 199 ns/sample in Node (`dsp.mjs`), half of it the hermite reads by integer indexes, ToInt32 once; in a worklet of each engine 126 against 199 Chromium, 130 against 223 WebKit, 162 against 185 Firefox (its scalar code was the fastest); with the filter of the voices in the lanes, bench-perf `--against` in Chromium (5 runs a side, every run under every one of before): the audio thread of S5 41.5 against 51.4 Mcps (−19%), of presets of the database −27% [AI] Wah Clav (4 notes × 2 voices, distortion), −26% [AI] Synth Brass (6 × 6), −21% [AI] Supersaw Lead (6 × 12, delay), the memory the same; the chain of the cores in a worklet −12…−24% Chromium, −13…−26% WebKit, −3…−7% Firefox; tested offline with impulse responses: `reverb-dsp.spec.ts`; the tables of its lines in `reverb-decay.ts` and `reverb-era.ts`, the chart draws them), `reverb.worklet.ts` registers the processor, `reverb.ts` creates the `AudioWorkletNode` once `loadWorklet` has added the module and posts param changes to it. The worklet modules register their processor with `registerStereoProcessor` (`fx/effects/stereo-processor.ts`: the AudioWorkletGlobalScope declarations, a mono input feeds both sides, a disconnected one is silence, `stop` ends it), their nodes are created with `STEREO_WORKLET_OPTIONS`. A worklet module must not import `@waveform/ui-kit`, `@waveform/preset-schema` (zod) or anything touching `window`/`document`. The synth core adds the limiter and the wavetable-osc modules itself, so specs that count `addModule` calls count only their module (`workletLoads` in `test-utils`). In a hot loop of JS (a worklet of the app, the probe of the perf build), don't chain calls per sample that return doubles through closures or polymorphic sites: V8 boxes every such result (a HeapNumber), so the audio thread makes garbage and burns CPU; run each stage over the block in typed arrays (the TS cores of before stage 5 did).
- The distortion runs in an AudioWorklet too (`distortion.ts`, `distortion.worklet.ts`): its core (`dsp/distortion`, `distortion-wasm.ts`, its params in `distortion-params.ts`; tested offline, aliasing included: `distortion-dsp.spec.ts`) drives the input (0 to 12 dB: more folds back audibly on high notes at 4×) into the curve of the mode 4× oversampled (the hard clip 8×, below) (`dsp-core/src/stereo.rs`: polyphase windowed sincs, `fir.sincPhase` in `libs/math`, linear phase, `DISTORTION_LATENCY` = 32 samples; the decimator is the one of the true peak detector, cut at the nyquist, the interpolator is cut at 0.9 × the nyquist, flat up to 0.4·fs: cut at the nyquist it passed half of the images of the partials just below it, which an oscillator plays, and the curve mixed them into inharmonic tones, so its phase 0 is not the input itself), × its makeup gain (`MAKEUP_TABLES` of `consts.rs`, worked out as `test-utils/distortion-makeup.ts` does: a table per mode over the drive that keeps the RMS of a reference sine of `REFERENCE_PEAK` 0.5, a note at the fx input; 1:1 with the drive while the reference is unclipped, then it levels off towards −9 dB, −7.1 dB soft and −8 dB hard at 12, so louder sounds come out quieter and quieter ones louder: the curve compresses), then the tone lowpass (at the top of its range, `TONE_OPEN`, it is faded out: the wet keeps the phase of the dry), the level (a trim on top of the makeup) and a DC blocker (one pole at 5 Hz, `DC_CUTOFF`: the curves are odd, but an asymmetric wave, a narrow pulse, gets DC from them, which would eat into the headroom of the limiter; the tests of the gains undo it, `unblock`); drive, makeup, level, tone and a new mode (a crossfade of the curves, each with its makeup; the mode changed back during a fade turns it around where it is) glide. The gains go on the oversampled points, before the decimator, so a crossfade never mixes points with and without them. The chart shows the curve of the mode at the drive within ±1, without the makeup and the level (they only scale the output). The modes are `DISTORTION_MODES` (`distortion-modes.ts`: soft clip = tanh, hard clip): the `mode` param is an index into it, so new modes are appended and `FX_PARAMS.distortion.mode.max` raised; a curve is odd, within ±1 and has the slope 1 at 0 (bitcrush would need a state of its own). It has no loops: `setActive` does nothing; once its input has been silent longer than the oversampler rings only the tails of the tone and the DC blocker are rendered (about 0.7 s after a DC-heavy sound, at 0.15% of a core), then the worklet clears its state and skips the blocks. Each stage runs over the block (`up`/`down` of the oversamplers and the `shape_block` of the mode, both channels in the lanes of f64x2), the output is the same to the bit as sample by sample. The TS cores of before stage 5 cost about 1% of a core while playing (soft clip 1.1%, hard clip 0.95%, reverb 2.6%), the Rust ones half (`dsp.mjs`), 0.05% unused.
- A worklet effect builds on `createWorkletFx` (`fx/effects/worklet-fx.ts`: loading, input → node → output, `$status`, `retry`, `destroy` posts `stop` to the processor, so does a failure: a processor that threw still takes it, its core is freed; a stopped processor takes no message). Without AudioWorklet (http on a LAN IP, old Safari) or when its module fails, the app still works: the fx model keeps the effect out of the chain (it stays `added` in the snapshot), and the Effects list shows why under its name. An unsupported effect can't be added, an added one that can't be used can still be removed, a failed one loads again on Retry or when it is added. Until an effect is `ready` (also while it loads) its slot passes only the dry signal and is inactive.
- The oscillators run in an AudioWorklet (`synth/common/wavetable/`), there is no native fallback: without AudioWorklet, Worker or MessageChannel the synth doesn't play and each oscillator shows why over its wave (`OscillatorStatus`, Retry for a module that failed: `retryAudio`, the limiter too if it failed); else why its table doesn't: the store refused it or the worker failed to build it (the previous one plays, Retry sends it again). `wavetable-engine.ts` (one per context, in the synth core): `$status` loading/ready/unsupported/failed (the module, the worker, the store or the voices node) and `retry` (as `createWorkletFx`), the store node (`STORE_PROCESSOR`, 0 inputs, 1 output never connected: 0/0 is not allowed), the voices node (`VOICES_PROCESSOR`, into `preGain`: every note), the worker (`wavetable.worker.ts` → `wavetable-builder.ts`) and a MessageChannel between them: `setTable(id, frames)` copies the frames into Float32Arrays transferred to the worker, the worker builds the levels (`wavetable-mipmap.ts`, a newer version of a table replaces a waiting one) and transfers them to the store; the store (`createTableStoreWasm`, one per AudioWorkletGlobalScope, refcounted versions in the memory of the core) answers `{stored, version}` or `{refused, version}` (no memory for it) and `{freedBytes}` once it frees versions. The engine hears the store and the worker in every build (the port started: nothing piles up in it): `$tables` gives each table `sending`, `stored`, `refused` or `failed` (the worker's `{failed, version, reason}`: a build that threw, an allocation of a phone; only an error of the worker itself fails the engine) for its latest version, `retryTable(id)` sends it again, a refused version goes again once when the store frees memory (refused again, it waits for Retry); the oscillator model has its own (`$tableState`, `retryTable`). Tables are kept and sent again after a retry, versions only grow. `createVoice(options, values)` makes the voice of a note in the voices node, null until ready (a note played meanwhile isn't played later): a `VoiceHandle`, its id and `params`, per param the AudioParam calls the synth makes (`ParamAutomation`: setValueAtTime, setTargetAtTime, exponentialRampToValueAtTime, cancelScheduledValues), each an event of the node (its value in f32, as an AudioParam keeps it; none once the voice has ended); `setRoutes(ids, routes)`, `setFilter(ids, filter)` one event for the voices that get the same; the events of a task go in one message (`{ events }`, a microtask sends them; `flush()` the specs), in the order they were made. The node posts after a block that has any `{ started: [[id, started, scheduled]], ended: [id] }` (the handle's `onStarted`, `onEnded`); an error of the voices node (`onprocessorerror`) fails the engine: it is stopped (`{ stop: true }`: its voices give their tables back), every voice ends (the synth lets their keys go), Retry makes it again; destroy stops it, telling none. For the perf suite and the specs (the perf build and Jest, under `__PERF__`): `pending()` (tables whose latest version isn't in the store yet) and `stats()` asks the store (`{stats: true}`: versions and bytes held, voices alive and their unison, samples played from mix tables or directly, mix builds and refusals, mix tables allocated and their bytes, counted by the shared of the core, `createVoiceSharedWasm`) and the worker (pending tables, freed-buffer pool, build ms), with the voices of the voices node and the events their timelines hold (`scopeVoices`, `events`); a voice with `trace` in its options is told started (the frames) once, the synth traces voices only while its `$voiceStarts` is observed (every voice that started late is told too, production included: the fx and Poly follow it; so is every voice of mono, on time too, `mono` of its options: the synth keeps its starts again until then).
- Levels (`wavetable-mipmap.ts`, `wavetable-levels.ts` has the layout without imports (`createLevels`, the harmonics and the length of each level), so the worklet bundles no FFT): a third of an octave apart on the grid of Chrome's PeriodicWave (`levelBase`: harmonics up to 1024 · 2^(−r/3), at most the frame's 1023, then a silent level of 1 sample), each 32 samples per cycle of its highest harmonic long, 512..4096 (`levelLength`), 1 guard sample before a frame and 2 after it; DC and the nyquist bin dropped, a frame at the volume of the file (not normalized, as createPeriodicWave does; level B of the plan), phases kept, frames of 16..2048 samples, `MAX_FRAMES` 256 (≈ 63.6 MiB). Building 256 frames takes ~150 ms (Firefox ~300).
- The voice (the core `dsp/wavetable-osc`: `voice.rs`, through `wavetable-osc-wasm.ts`, its options and messages in `voice-options.ts`; tested offline: `wavetable-osc-dsp.spec.ts`; `wavetable-osc.worklet.ts` registers the voices processor and the store): every note is a voice of the voices node (`VOICES_PROCESSOR`, one per context; `voices-processor.ts`, its core `createVoiceScopeWasm`, `scope.rs`), both oscillators (null in `options.osc`: off for the note) with their unison voices; the node renders its voices in the order they were made by the same `Voice::process` and sums them in f32 in that order into one stereo output. A voice comes as an `on` event (its options and the values of its params at the note on) and its params as automation events, each param of each voice a timeline of the core (`timeline.rs`) with the semantics of an AudioParam: setValueAtTime, setTargetAtTime, exponentialRampToValueAtTime, linearRampToValueAtTime (bench-osc's LFOs; the synth makes none), cancelScheduledValues, by the formulas of the Web Audio spec in f64 from values in f32, each value in f32 clamped to the range of its descriptor (`VOICE_PARAMETERS`); an event acts from the first frame not before its time, one that comes later (a message comes between the quanta, automation came synchronously: a release or a knob may be a quantum later than it was) from the block it comes in, one of the same kind at the same time replaces the one there (as Chromium), the events of a voice that has ended are nothing, those the history of 0.5 s has passed are forgotten (their value kept); a block without a change is one value (as a browser gives a param without automation). The volume is ENV 1 (`envelope.rs`, exact to the sample, the release from the level reached); the voice ends where ENV 1 is back at 0 and the node tells it ended (it leaves the node in that block). A voice processed after its start (the render lag: its note on came a device buffer late) starts its envelopes at its first sample (`startAt`), the attack is not skipped; a note of a legato phrase starts them where the first voice of the phrase did (`join_phrase`/`phrase_frame` of the shared, `shared.rs`: the phrases of the scope by the frame they are scheduled at, each kept while a voice of it plays, so a note out of legato in between doesn't hide one; its first voice was created before, if it hasn't started it starts in the same block), so the voices of a phrase stay in step. The release starts h after the first sample of the voice (or its last start again; the key held h, the note on and the gate each reach the audio thread with a lag of its own), not before the sample the gate is seen at, at most `RELEASE_LEAD` after it. Routes (`modulation.rs`) replace the params they move (position, spread, gain of each oscillator; the knobs of the filter) by base + Σ amount × level (base × 2^Σ for a log one), clamped to the knob's range (the pitch of an oscillator, Semi and Fine, is two params of base 0, each clamped to the bounds of its routes: the range of its knob from its value; the voice adds them to the detune, with the bend on it, only where it reads it: its first sample and the points of the pitch, `Detune` of `voice.rs`, without such a route the detune as it is); while every envelope a param follows is in a flat stage and its amounts don't glide it is one value (the voice stays on its mix table), an envelope no route reads is not rendered, a changed route glides in 10 ms (a `routes` event; its polarity too: the ½ a bipolar one takes off its level glides). The oscillator model holds it (`$unisonShape`, `setUnisonShape`: no knobs and not in the snapshot or the schema yet; the perf hook reaches it through its models). The knobs of the native nodes (the delay: Time on both lines, Feedback on the gains of a line into itself and on those into the other one, a line each, while its mode is on and the delay active: another mode glides one out and the other in, Pan on the delay of each side, Freq and Q k-rate; the dry and the wet gain of every slot) follow their routes by the lines of the fx-mod worklet (`fx-mod.ts`, `fx-mod.worklet.ts`, `fx-mod-lines.ts`, `fx-mod-params.ts`: one node of the fx model, no input, an output of one channel per line, `FX_MOD_LINES` 13): the offset map(the knob moved) − map(the knob) (`mapKnob`: the pan split at 0, the equal power or the linear mix) worked out at points every 32 samples and the last of a block, linear between them, added to the params, which stay at the knobs with their glides (Time with its tape glide; a message a quantum late only shifts the start of the offset, no Time or mix of 0 a quantum long); a change (a route, a knob, a new note) glides from where the line was in 10 ms (`FX_MOD_GLIDE`), a line gone goes to 0 so and is disconnected then (a line is connected only while it has routes: an a-rate input costs every sample); until fx-mod is ready no route moves them, the knobs work. `fx-automation.ts` only steps and glides the params of the knobs (the routes have no automation of theirs: the corners of an envelope could not lead an LFO, and timers throttle in a background tab). The osc/fx switch (`TapeSwitch switchOnDrag`) flips when a dragged label stays on it 600 ms.
- LFOs (`synth/common/lfo/lfo-curve.ts`, no imports but the curve of the envelopes, shared by the main thread, the fx worklets and the specs; the core `lfo.rs` does the same operations in the same order, but for a route of Rate: its base in f32 as the routes read it): LFO 1–4, sources 4–7 of the routes after VELO, each a cycle of its shape (a table of `LFO_TABLE_SIZE` 2048 + 1 levels 0..1 the TS builds: `lfoTable` of sine, triangle, saw up and down, square or of `points` [x, y, k] of its own, the curved segments of the envelopes, the last one over the end of the cycle (the preset takes them; the Shape select offers them by category, `synth/lfo/lfo-shapes.ts`: Basic the shapes, Sidechain, Rhythm and Steps points (`setPoints`: the preset keeps them, a change of the list changes no sound), others Custom, `shapeOptionOf` within the 4 digits of a preset); `lfoTableFrom` any cycle) every `rate` seconds (its period, 10 ms..32 s: the knob goes by the frequency, right faster, and shows the period). The clock of each LFO is the anchors of the main thread (`nextAnchor`: a new period from now + `LFO_LEAD` 10 ms, at the phase there: no step; the newest four kept), a note runs it from the start of its envelopes (`createLfoRunner`, `LfoBlock` of the voice: at the points of the routes, every 32 samples and the last of a block): during Delay the left point of the shape (its level at the start of the cycle; tD the first point past it, at s + Delay), Rise morphs it into the shape linearly, Smooth lags it by one pole (seconds; its coefficient by the frames between the points), Phase shifts the cycle (around it; a new one glides by the shortest arc in 10 ms); retrig plays the cycle from tD (φg(t) − φg(tD) + δ), free the clock (φg + δ), the mode live (a playing note switches at once, as if it had played the other one all along); δ is the phase a route of Rate adds (∫ of the frequency it moves to − the knob's, from tD); a new shape crossfades in 10 ms from the one it plays at its time: until then the crossfade before goes on (`pending` of `createLfoGlobal`, `pending_table` of `lfo.rs`: a third shape meanwhile takes the one waiting as played from now on; the mixes are baked into two buffers of the global, the tables are those of the states: a state allocates nothing on an audio thread). A note of a legato phrase starts them where the phrase does, a start again (mono) starts them again (retrig from 0, Delay and Rise again, the smoothing goes on), a late voice at its first sample; one LFO per note, not per unison voice, on in the release. Their knobs take the envelopes and VELO (`lfoN.rate|delay|rise|smooth|phase`: Rate in octaves of its frequency within 1/32..100 Hz, the times a share of their travel, `pow`: max · (share + Σ)⁴, Phase around the cycle, not clamped), no LFO (the schema, the model, the drag and the core drop it). The `lfo` model (`lfos.ts`, snapshot `lfo: { l1…l4 }`, `LFO_DEFAULTS` a sine of 0.5 s, retrig; `$selected` the tab of the section, the UI) sends every change as a state from now + 10 ms, at most every `LFO_STATE_INTERVAL` 20 ms (`throttleTime`, the first change at once, the last one after the pause: a drag posts 50 states a second at most, to five threads, a table of 8 KB each when it is a shape; a shape never comes while the one before still crossfades) (`LfosState`: the knobs, the newest anchor of each clock, the tables of the shapes that changed; `$changes`, `$state` with every table; one that reaches an audio thread after its time takes over at its next block, `lateState` of the voices processor, the fx worklets and fx-mod: its Phase still glides, its shape still crossfades, its anchors keep their times): to the voices node (a `lfos` event in the order of the others), to the fx and their worklets, and runs them on the main thread (`globals`). A consumer takes the states only while it reads an LFO (`createLfoFeed` of `lfo-curve.ts`: the engine while a voice of the node has a route of one, `lfoVoices`; the reverb and the distortion while their modulation has, fx-mod while a line has; meanwhile the states are merged on the main thread, `mergeLfos`, the LFOs as they are go first, instantly, once it reads one, before the message with the route; a node made later, ready or Retry, starts with them, `initial`): a state is a message every audio thread deserializes, a table of 8 KB allocated there. In the core the LFOs of a node are in the shared (`LfoGlobal` × 4: the clock, the knobs from the time of a state on, the shapes; `osc_shared_lfo_table`, `osc_shared_lfos`; a state wakes the routes of the voices, `lfo_epoch`); a voice runs those a route of a param reads (`modulation.uses_lfos`; a second `Modulation`, `lfo_mod`, moves their knobs; one value while in its Delay or on a flat shape: the voice stays on its mix tables), without a route of an LFO nothing new runs (the goldens of before to the bit). The fx follow the LFOs of the last note (`createNoteLfos`: from its start, on their clocks without a note, their Delay and Rise passed), the marks of the knobs and the chart too. The section (`synth/lfo/`: right of ENV): the tabs LFO 1–4, a cycle of the shape shown edge to edge (the levels 4 px in: a point of the editor whole) on the lines of the chart of an envelope (levels 0, ½, 1, the quarters) with the dot of the last note (the one of an envelope, `NOTE_DOT_RADIUS`/`NOTE_DOT_COLOR`; `onFrame` of ui-kit, on a canvas, no render; cleared without a voice) and its points on it, edited there (`lfo/components/lfo-points.tsx`, the math in `lfo-edit.ts`, pure: a list the model takes or null): a point dragged within its neighbours (onto one: a step; the first stays at x 0; x and y to 0.001, `movePoint`), the point of the curve of each segment that rises or falls and is 12 px wide at least, the last one to the start of the cycle too (`CurvePoint` of ui-kit, exported for it; `setCurve`), a press within 6 px of the line (`nearestSpot`: the projection on the nearest segment of the 257 samples of the chart, a step a vertical one; a translucent point shows it, cursor copy; the points are filled, the points of the curves hollow; not within the hit area of a point, nor at `LFO_POINTS_MAX`) adds a point there (`insertPoint`: on the curve of its segment, which keeps its shape exactly: an exponential segment over a part of it is one of k × the share of the part, so the parts take k by their shares, `envelopeCurve`) and drags it on, a double click takes a point out (`removePoint`: two stay, the first too; the segment before keeps its k). A shape of the LFO shows as points too (`shapePoints` of `lfo-shapes.ts`: triangle, the saws and the square exactly, the sine four curved quarters of k ±1.7, within 0.022 of it) and is those points from the first change on (`setPoints`: Custom in the select); every change sends the table to the audio threads, the sound follows the drag. Shape and Mode, the knobs Rate, Delay, Rise, Smooth, Phase (targets). Specs: `lfo-curve.spec`, `lfos.spec`, `lfo-edit.spec`, `lfo-points.spec`, `lfo-shapes.spec`, `lfo-chart.spec`, the `LFO` describe of `wavetable-osc-dsp.spec` (a voice against the voice given the levels of the TS runner: to 1e-6), `lfo.rs`, `modulation.rs` and `tests.rs`, the LFO goldens, `fx-modulation.spec`, `fx-mod-dsp.spec`, `fx-mod.spec`, `lfo-section.spec`, `use-knob-modulation.spec`.
- `input-controller.ts` is the shared note-on/off bus: `$onPress` carries the note and its velocity (MIDI 1..127; QWERTY and the piano play `DEFAULT_VELOCITY` 100), `$bend` the pitch bend as a share of its range (−1..1, 0 at rest; the last of the MIDI input and the wheel wins). The on-screen piano, `keyboard-controller.ts` (QWERTY) and `midi-controller.ts` (WebMIDI) all feed into it. The MIDI controller passes the velocity of a note on and the pitch bend of its channel (`0xE0`, `midiBend`: 14 bits, 8192 at rest, 8191 steps up and 8192 down; one within `BEND_NOISE` 2 steps of the last one it set on its channel moves nothing while that one plays (the wheel on the screen set none since): the noise of a wheel, every new bend takes the voices off their mix tables; rest and the ends come exactly), and puts the bend it set back at rest where it releases its held notes (another channel, another input or none; the bend of the wheel stays, one it set after the MIDI input too). The wheel (`synth/pitch-bend/`, `PitchWheel` of ui-kit: a dark drum in a slot, as high as its place, its ribs and the mark where they are as it turns, ±60° over the range, the mark follows the pointer; it shows the bend once a frame; a drag gives values against its own last one, not the one shown a frame late, and its section is memoized: the keys render on every note) springs back to 0 when let go, on blur and on a lost pointerup. On a desktop it is in a section of its own left of the keys with its range Up/Down, the bottom row as high as the keys (`KEY_HEIGHT`), the keys narrower to fit; on a phone alone (its range is the preset's), in the column left of the keys (`keys-view.tsx`): in portrait under the octaves of both tiers, in landscape left of both tiers, as high as them. The MIDI input and channel the user chose are kept by the tab (sessionStorage `midiInput`, `readStored`/`writeStored` of `app/common/services`): the chosen input is selected whenever it is connected, meanwhile the selected one while it is, else the first one (selected for the user, not kept).

### Rust cores of the worklets (dsp/)

- The DSP of the worklet modules is Rust → wasm32, one `.wasm` per worklet bundle (`dsp/<crate>`, a cdylib with a C ABI, no wasm-bindgen and no SharedArrayBuffer), ported bit for bit from the TS cores, which were removed at stage 5 of the plan (two weeks in production without a regression; the goldens hold the sound since): a bundle `<name>.js` (`<name>.worklet.ts`) registers its processors (names in `common/processors.ts`) with their AudioParams and messages, its facade (`<name>-wasm.ts`) wraps the core, the options and messages are in `limiter-params.ts`, `reverb-params.ts`, `distortion-params.ts`, `wavetable/voice-options.ts`. A module with a core needs wasm SIMD (`isWorkletSupported(ctx, name)`, `WASM_MODULES` of `common/wasm/wasm-support.ts`: `unsupported` without it: the limiter and the oscillators are silent). The cores: the limiter (`dsp/limiter`), the reverb (`dsp/reverb`), the distortion (`dsp/distortion`), the wavetable oscillator with its store (`dsp/wavetable-osc`).
- The crates: `jsmath` (the Math of JS bit for bit: V8's fdlibm of `deps/v8/src/base/ieee754.cc` for sin, cos, exp, expm1, tanh, log, log2, log10, glibc's pow without FMA, as V8 calls std::pow; `round`, `max`, `min`, `to_int32` with the JS semantics; `jsmath-check` exports it to the specs), `dsp-core` (biquad coefficients and TDF2, the blocks of the effects, true peak, oversampler, the stereo io; `consts.rs`: the tables the TS cores worked out when their modules loaded, as the bits of each double, now its source), `simd.rs` (`F64x2`: two independent lanes, the operators of f64 and the `min`/`max` of wasm, which are those of Math) and `stereo.rs` (biquad, DC blocker and oversampler of both channels in the lanes: the distortion renders L and R at once; `LaneBiquad`, two filters of coefficients of their own: the shelves of two lines of the reverb), `blocks.rs` (`DelayLine::read_pair`, `Allpass::process_pair`: two lines in the lanes, their hermite indexes as integers, ToInt32 once; `StereoDelayLine`, `StereoFixedAllpass`: a ring of both channels). `cargo test` runs the lanes as arrays (`simd.rs` off wasm): the specs of the crates hold each lane to the scalar block, only the goldens in Jest run the SIMD of wasm, one crate per core. On wasm32 the crates are `no_std` (`wasm-rt`: a panic traps, dlmalloc as std uses it; `jsmath::floor/ceil/trunc/sqrt` are the wasm instructions), natively std (`cargo test`). `dsp/rust-toolchain.toml` pins the toolchain, `.cargo/config.toml` builds with `+simd128`, a 64 KiB stack and `__stack_pointer` exported (a trap leaves it moved, about 70 failed note ons used up the stack: every call of a core puts it back, `instantiateCore` wraps the exports, the calls of a block guard it where they are made, `fx_buffers` and `fx_process` in `stereo-core.ts`, `osc_io` and `osc_voice_process` in the voice, `osc_scope_process` and `osc_scope_resume` in the scope; a trap pins nothing: `Voice::new` only allocates, `attach` joins the phrase and takes the versions once the voice is boxed (the scope reserves its place before), its end gives the versions back before the mixes, a mix without memory plays directly, the store reserves the room of an entry before it takes a slot and never traps holding a buffer), `panic = "abort"`, fat LTO.
- The sound: a core computed every value as its TS one did, bit for bit (the same operations in the same order: no `mul_add`, no fast-math, no relaxed-simd: SIMD only over independent lanes, sums in their order, `as f32` where the TS wrote into a Float32Array, the Math of jsmath; "as the TS" in a comment of a crate names such an order), the goldens hold it since. Changed since, by explicit updates of the goldens: the voice played the two frames of a moving position in f32x4 (within 8.3·10⁻⁷ of before, 131–154 dB below the signal), then one frame at a time, discrete (the scenarios with a fractional or a moving position; the others bit for bit), then a change of frame fading in over a period, at most 5 ms (the 5 scenarios whose frames change, with their sums of one node), then the steps of a moving pitch, one pow a point (within 15 ulps, most within 2), and the mixes within the reach of a moving pitch (the 2 scenarios whose spread an LFO moves or whose pitch the bend moves, with their sums of one node; the others bit for bit), then the glide of the levels a voice reads when the mix it plays changes (the scenario of the bend, with its sum of one node; the others bit for bit). The goldens: `<module>-goldens.spec.ts` renders the golden scenarios block by block (their hashes in `dsp/goldens/<module>.json`, `UPDATE_GOLDENS=1` records them again: a change of the sound is an explicit update) and random ones (`test-utils/fuzz-signals.ts`, `FUZZ_SCALE`; the nightly run × 250): finite, never over the ceiling of the limiter, every voice ending and giving its tables back. Node's own Math differs by machine (on arm64 its fdlibm is compiled with FMA contraction, its pow is the libm of the system), so the goldens specs import `test-utils/js-math.ts` first (Math becomes jsmath, the inputs and the levels the TS builds are the same everywhere; `**` runs as `Math.pow`: the babel plugin of `jest.config.ts`); `jsmath.spec.ts` checks jsmath against Node (x64: bit for bit, arm64: within 4 ulps) and against the hash of its outputs. The DSP specs of a module (`<module>-dsp.spec.ts`) run its core through its facade. The specs load `tmp/wasm-perf` (`test-utils/wasm.ts`, `wasm-transform.js` for the bytes a bundle imports): `npm run wasm` first.
- The wavetable oscillator (`dsp/wavetable-osc`: `envelope.rs`, `lfo.rs`, `modulation.rs`, `filter.rs`, `store.rs`, `shared.rs`, `voice.rs`, `timeline.rs`, `scope.rs`; `wavetable-osc-wasm.ts`, `wavetable-osc.worklet.ts`): one instance per AudioWorkletGlobalScope holds the store, the shared and the voices (handles: `osc_store_new`, `osc_shared_new`, `osc_scope_new(rate)` the voices of a node with the ranges of the params, `osc_voice_new(rate, store, shared)` a voice alone, the facade the specs use; the specs make several stores and shareds in one instance). The scope (`scope.rs`, `createVoiceScopeWasm`): `osc_scope_on` (the options of a voice and its values in `osc_command`), `osc_scope_events` (the automation events of a message, 6 values each in `osc_command`), `osc_scope_routes`/`osc_scope_filter`/`osc_scope_velocity`, `osc_scope_bend` (the pitch bend of the node), `osc_scope_process(frame, frames)` (every voice: its 10 timelines or the arrays given by `osc_scope_direct`, the specs, then `Voice::process`, its output added to the sum at `osc_scope_output`), `osc_scope_fail` and `osc_scope_resume` (a voice that trapped ends, the block goes on with the next one; `fail` is false when the trap was not in a voice: the block is silence), `osc_scope_reports` (the starts and the ends since the last call), `osc_scope_tap`/`osc_scope_taps` (the output of every voice apart: the goldens of the scope, the parity of the browsers), `osc_scope_stats`, `osc_scope_free` (its voices end). The versions of a table live in the memory of the core (a slab, refcounted: `EntryRef`), a version no one holds gives its buffer to a pool (2 at most, the samples of one table of 256 frames at most): the smallest buffer of it that holds a table takes it, none does: the pool is freed before one is allocated (two sizes in turn: the memory stops growing after the first switches; a table that grows a frame at a time to 256 takes 239 MiB, two versions of up to 63.6 MiB live while the next comes and what dlmalloc can't join), the placeholder sine is the store's. A table arrives in chunks: the wasm store posts `{ chunks: STORE_CHUNK }` (1 MB) to the worker once it has its port, the builder (`wavetable-builder.ts`) then sends `begin` (the layout: `osc_store_begin` only reserves the room of the version) and the data chunk by chunk (`osc_store_chunk` gives the room of each in order and within the length of the version, zeroing only the chunk: the begin of a table of 256 frames 19 µs, it zeroed 64 MB on the audio thread; `commit` refuses a version a chunk of which is missing), the next once the store acked the last with its buffer (`createStoreReceiver`: a chunk is acked whatever happens to it, one that fails aborts its version, `osc_store_abort`, refused; the worker sends `{abort}` for a version it stopped sending, the port of a new worker aborts every slot and the receiver of the store processor before it drops what still comes, `epoch`), then frees its levels at once (`transfer(0)` detaches their buffer: kept for the next build, or left to a GC of the idle worker, a table of 256 frames stayed in it next to its copy in the core, S5 +68 MB; Safari before 17.4 leaves it to the GC), and the store replies nothing freed; a version the core has no memory for is `refused` (`try_reserve`), the latest one plays on. A version posted whole to its node (the offline engine of the specs, bench-osc) is copied in at once. The options of a voice (table ids interned per scope, the 8 random shares of each oscillator drawn by the facade in the order of the TS, then its `UnisonShape` and, for a random detune, 8 more), its routes (param names as ids, 7 values each: source, param, amount, min, max, scale, bipolar; the oscillators ids 0–9 (position, spread, gain, pitch, fine each: pitch and fine offsets of the detune of base 0), the filter 10–12, the knobs of the LFOs ids 13–32), its filter, its velocity and the states of the LFOs (`setLfos` of the shared: the tables, then the knobs and the anchors) go through `osc_command`, the 10 params of a block through `osc_io` (one value or `frames`), the outputs through `osc_io_output`. `voices-processor.ts` is the voices processor of the worklet: the events of `processorOptions.events` before its first block, those of its port in order, a report after a block that has one; `tap` puts voice k in channels 2k and 2k + 1. The render loops wrap the phase in a cold call (else LLVM makes the wrap a select on the chain of the phase, a third slower than V8's code of the TS) and two neighbouring unison voices that both play their mixes render in one loop (`render11_pair`; their builds are decided first, in their order, so the budget and the counters stay those of the TS); a voice that fades from a frame into another reads both in loops of their own (`render21_same` on one level, the loop of two levels of one length; `render22_same` on two of one length: the four windows in the lanes of an f32x4, `render22` on two of other lengths, restored from before discrete frames, where they morphed frames k and k + 1; `render_fade`, which calls them, is not inlined: a call of the voices that fade only; inlined into `render_voices` with `render_span`, the loops of a frame alone, they cost a voice held on its mix table 5% in Node, `voice u1 held`, its registers); frames are read through windows checked once per span, a mix is built over slices checked once (a check per read made the Lagrange upsampling of the short levels a quarter slower). Specs: `wavetable-osc-dsp.spec` and `wavetable-osc-budget.spec` (`test-utils/voice-dsp.ts`: a scope of voices of one instance of the core per spec file), `wavetable-osc-goldens.spec` (scopes of voices on a store and a shared, the envelopes curved as the app gives them; each scenario again as the voices of one node, the params as the arrays of each block through `osc_scope_direct`, every voice tapped: the same hash, and the sum of a block the f32 sum of the voices in their order, its own golden `<scenario>: the sum of one node`; random scopes both ways, and with a voice that traps), `wavetable-osc-scope.spec` (the timelines against the formulas of the spec through a voice, bit for bit; the order, the sum, the reports, a trap), `wavetable-osc.worklet.spec`, `wavetable-memory.spec` and the chunks of `wavetable-builder.spec`.
- The distortion core oversamples the hard clip 8× (the TS core did 4×: level B of the plan): a chain of its own (`StereoOversampler8`, `UP8_PHASES`/`DOWN8_PHASES` of `consts.rs`: `fir.sincPhase` at 8×, 32 taps per phase at the input rate as the 4× one, so the latency stays 32 samples), the soft clip stays on the 4× chain. A fade between modes on two chains runs both, each with its curve and its gains, their outputs added at the input rate; a chain that starts takes the input history of the other (its interpolator as if it had run, its decimator at 0: its points weighed 0 before), one that stops flushes its decimator with points of 0 for 33 samples, so the output is the one of both chains running all the time (the spec of the crate checks it). Hard clip of 7 kHz at 12 dB: aliases at −62.8 dB (4×: −50.2), 10 kHz −56.7 (−44.5); soft clip unchanged.
- A core: `fx_new(rate) → handle`, `fx_buffers(handle, frames)` (inL, inR, outL, outR in its memory, grown before the block), `fx_process(handle)`, `fx_clear(handle)` (forgets the sound before: a `{ clear }` message of `registerStereoProcessor`), `fx_free(handle)` (`stereo-processor.ts` frees it on `stop`); `stereoCore` keeps Float32Array views on the memory, made again when it grew (`createView` of `wasm-core.ts`; a pointer comes as an i32 and is read unsigned: past 2 GiB it is negative). The options of `fx_new` and the messages go through `fx_command` (a Float64Array in its memory): the reverb's `fx_set(handle, routed)` reads a count and key/value pairs (one `set` of the TS: the line scale follows once), the distortion's a bitmask of the keys present and the params; `fx_set_active`, `fx_idle`. Allocations only in constructors and when a buffer grows, never in a block. The functions of a core compile lazily, on their first call (the first block of a voice 0.93 ms in Node, then 0.014): each worklet module renders a few blocks of its own dsp while it loads and frees it (`prewarmStereo` of an impulse, over the ceiling of the limiter; the distortion both curves; the oscillator a voice of both oscillators on the placeholder sine and a table of 2 frames of silence (`createLevels(2, 32)`: the fades of a frame at the pitches of their three loops), with a store and a shared of its own, a route of LFO 1 and routes to its knobs (a flat block in its Delay, a new Phase gliding, a new shape crossfading), a moving position, then a steady one), so neither the constructor nor the first block of a processor compiles them (the modules load with the app; the oscillator's prewarm takes 2 ms, before the first note). The distortion and the reverb take NaN and the infinities as 0 (`finite_inputs` of the stereo io before a block, a finite input to the bit; one silenced the distortion for good and the reverb until it was off), a block whose peak isn't a float clears the state and is silence; `wav.ts`, the decoded files and the worker take such samples as 0 too (the native delay holds a NaN in its loop in Chromium and WebKit). The fuzzers of the effects keep to what the app sends them (NaN, the infinities and 1e30 in their input too, the params in their ranges, beyond the top only where the core stays finite: a decay or a bass beyond its range blows the loops up, the knobs and the modulation never go there).

### Snapshots

`app/plugins/snapshot.ts` creates one `searchParamsSnapshotPlugin`. Models that register it (`osc1`, `osc2`, `filter`, `env`, `mod`, `fx`, synth as `v`) expose their state as `{ [modelName]: { key: value } }`:

- `getSnapshot()` / `applySnapshot(obj)` read and apply the state at runtime (used by presets); `$snapshotChanges` emits on any change.
- Legacy URL params `<modelName>-<key>=<json>` are still applied on init.
- `applySnap` must handle falsy values (`!== undefined`, not `&&`), and missing keys mean defaults.
- When adding persisted state, extend the model's `modelToSnap`/`applySnap` **and** `presetDataSchema` in `libs/preset-schema` (unknown keys are stripped, so a missing schema field is silently not saved).
- Oscillator keys: `o`, `s`, `f` Oct, Semi and Fine (whole octaves ±3, semitones ±24 (`SEMI_MAX`), cents ±100 (`FINE_MAX`); a preset or url saved before Semi and Fine gets 0: it sounds as it did, the hashes of the database changed with them), `d` the unison detune (its spread), `w` is the Wave position in the frames played (fractional; of a table with a morph mark among its 256: the presets saved before discrete frames had it in the frames of the table: an update of the database recalculated them, frame j of a table with a morph mark to `keyFrame(j)`, a position past the end of the table to its last frame), `ph`/`pr` Phase and Phase rand (0..1, default `DEFAULT_PHASE` 0.5 = 180° and 1). A legacy `r` (Phase rand as a start delay of 0..2 ms) is read only: without `pr` it becomes `pr = min(1, r / 0.002)` (`withLegacyPhase`, in the schema, `applySnap` calls it for legacy urls) and is not written; such a legacy preset or url without `ph` gets `LEGACY_PHASE` 0 (it played from the start of the wave), not the default.
- LFOs `lfo`: `l1`–`l4`, each `rate` (the period, seconds), `delay`, `rise`, `smooth`, `phase`, `shape`, `mode` and `points` of its own (optional); every preset has them (its hash changed with them: the hashes of the database are worked out again by SQL once it is deployed). Routes of an LFO are `lfoN:<knob>`, a bipolar one `{ a, bi: true }`; a route switched off has `off: true` (`{ a, off: true }`, `{ a, bi: true, off: true }`; a number is a route on).
- Voicing `v`: `leg`, `port`, `max` and the range of the pitch bend down and up, `bd`/`bu` (semitones 0..24, 2 by default; those of a url snapshot whole within it, one that isn't a number the default: `bendRangeFrom`, Infinity would bend by NaN cents). Envelopes `env`: `e1`–`e3` and the knobs of the velocity `vel` (`amp`, `k`; a fresh preset and Init: Amp 1, a line); the presets of the database saved before the velocity get Amp 0 by an update of the database (they sound as before), routes of VELO are `velo:<knob>`.

### Presets (apps/waveform/src/app/presets, netlify/functions)

- `libs/preset-schema`: zod schema of preset data with ranges and defaults, `normalizePreset` (4 significant digits, sorted keys), `presetHash` (sha256 of normalized JSON, name excluded → dedup), profanity filter. Shared by the client and functions (functions import it by relative path, esbuild doesn't know tsconfig aliases).
- API (Netlify Functions v2, routed by `config.path`): `presets.mts` handles `/api/presets` (list/search with keyset cursors, save with Turnstile + 5/hour/IP), `/api/presets/top`, `/api/presets/:id` (GET, and PUT to overwrite), `/api/presets/:id/report`, `/api/presets/:id/opened`, `/api/presets/name-available?name=`; `usage.mts` stores listens and stays (each with a Turnstile token of its own). IPs are stored only as salted hashes.
- Scheduled: `recompute-scores.mts` (every 30 min) and `cleanup.mts` (daily, removes unqualified presets 90 days after they were saved, edited or opened by their author: `GREATEST(created_at, updated_at, author_opened_at)`; listeners not heard for 60 days; reports of hidden presets and those older than 180 days, so REPORT_HIDE_THRESHOLD counts the reports of half a year).
- Scores (`recompute-scores`, last 60 days): a listener is an `ip_hash` (`getIpHash` hashes `ipKey`: IPv4 as is, IPv6 by its /64, privacy addresses rotate), not a client id (clearing localStorage would make new ones). A listen is playing a chosen preset `USAGE_LISTEN_SECONDS` (10), a stay `USAGE_STAY_SECONDS` (60, both `libs/preset-schema`), both without switching to another one; presets skipped sooner are not counted (the top is stepped through with ◀ ▶ the most, their listens would weigh against it). The client sends each once a preset is opened (`POST /api/usage` `{ presetId, event: 'listen' | 'stay', turnstileToken }`), `usage.mts` keeps one `listens` row (migration 004) per preset and IP with the days of the last listen (`heard`) and stay (`stayed`, NULL if none), each renewed at most once a day; a stay sets `heard` too, so `stayed <= heard`. Listens on hidden presets and on the author's own ones (the preset's `ip_hash`) are not stored, the preset opened on start is not counted at all (its listeners didn't choose it). Each listen and stay weighs w, a 7-day half-life since its day. `score` = the share of listeners who stayed with a Bayesian prior: (Σ w stays + k·m) / (Σ w listens + k), m the site's share: Σ over all presets of their shares, each weighing min(Σ w listens, k), k = SCORE_PRIOR_LISTENERS (with every listen counted the top would make the average itself and its lower part would keep falling below it, out of the top); a share, not a count, so the top's extra traffic (start, ◀ ▶) gives it no extra score, and a preset with few listeners stays near m. `unique_users` = the listeners who stayed (shown in the lists). Only presets with MIN_UNIQUE_USERS of them get a score (and `qualified_at`). `cleanup` removes rows not heard for 60 days.
- Popular: `preset_scores.popular` with POPULAR_MIN_USERS listeners who stayed and a share not below m (m is a rounded numeric quotient, compared with a 1e-12 tolerance, so exactly the average counts): the bar doesn't grow with the audience, a preset found in the list gets in with listeners who stay. `/api/presets/top` (Popular tab, ◀ ▶, 50 presets) has every featured preset first (curated, `presets.featured`, whatever its score), the rest of it are such presets by score; the `popular` sort of the list orders all presets by score, whatever the threshold.
- Client: `presets` rxModel (current preset, dirty flag via hash comparison, ◀ ▶ list, `?preset=<id>` loading; a preset and Init are applied through the sound switch, its `setCurrent` too (a preset that throws as it is applied: a toast, it doesn't become current), the restore of the tab at once; specs without the synth pass `immediateSoundSwitch` of test-utils), `usePresetUsageTracker` (counts the seconds an opened preset is played: audio runs, tab is visible and a note is held or was played or released in the last 30 s; once a preset reaches `USAGE_LISTEN_SECONDS` / `USAGE_STAY_SECONDS` without switching it reports the listen / the stay, each once; the `auto` preset is not counted until it is chosen; another preset drops a listen or stay not reached, a hidden tab only pauses it), `UsageReporter` (rendered by `PresetSection`) sends them one at a time, each through a Turnstile widget of its own (`appearance: 'interaction-only'`, out of the layout, the script loads with the first event): the visitor never sees it, an event Cloudflare would ask to interact for, a failed check or no token in `CAPTCHA_TIMEOUT_MS` (30 s) is dropped.
- Start without `?preset=`: `openPopular` opens a random one of `/api/presets/top` as `auto` (unless something was loaded, saved or changed meanwhile: the state must still hash to `presetHash({})`). Random, not the first: no single preset is opened for every visitor; ▶ continues from it. An `auto` preset is not put in the url (after a reload it would open from the link as chosen). Init (the button between the name and ▶, `reset`) applies `normalizePreset({})` (not `applySnapshot({})`: some `applySnap` keep missing keys), clears the preset and the url. The tab keeps what a reload would lose (sessionStorage `presetState`: the current preset, its loaded hash and the params, written 200 ms after a change and on `pagehide`): an edited preset, the `auto` one, an edited Init; not a clean preset (its link opens it) nor Init itself (the start opens a popular one). On start it is applied (through `normalizePreset`) instead of loading when its preset is the one of the url (none for `auto` and Init), so a link to another preset in the same tab opens that one. UI: `PresetPanel` in the header, `PresetBrowser` and `SaveDialog` antd modals. Cmd/Ctrl+S opens the save dialog.
- Editing: on create the server returns a secret `editToken` (only its sha256 is stored in `presets.edit_token_hash`); the client keeps tokens in `localStorage.presetEditTokens`. `PUT /api/presets/:id` with the token overwrites sound and name (no Turnstile, 1 update per 5 s, 409 if the sound is another preset's). Presets created before migration 002 have no token and can't be edited. Opening an own preset (`applyPreset` with a token in `localStorage`, once a session) posts the token to `POST /api/presets/:id/opened`, which sets `presets.author_opened_at` (migration 005, at most once a day, a wrong token changes nothing): the author keeps it from the cleanup.
- Names are unique case-insensitively with collapsed whitespace (`presetNameSchema` normalizes, `presets_name_key` is a unique index on `lower(name)`, migration 003). Hidden presets keep their names. The save dialog checks availability while typing; saving the same sound under a taken name still returns the existing preset (dedup by hash comes first).
- QWERTY notes are ignored while focus is in a text field (`keyboard-controller.ts`); a keyup releases only the note its key pressed, whatever the modifiers (not one of MIDI or the piano), and all of them are released when Cmd is (macOS sends no keyup of a key let go while Cmd is held) or the window loses focus (`$blur` of the app model). The on-screen piano releases a key on blur too, and a pointer that moves without a button (its pointerup lost).

### Wavetables

- The Netlify functions (`netlify/functions/get-wavetables-list.ts`, `get-wavetable.ts`) list the wavetable files in an S3 bucket as a folder tree and serve them. The client fetches the list with react-query (`synth/oscillator/hooks/use-wavetables.ts`). The table itself is loaded by the oscillator model from `$waveTablePath` (last path element = S3 key, `synth/services/wavetable.ts`, cached per session, 2 retries), so it follows presets whatever screen is shown; `WaveSelector` only shows `$waveTableLoading`.
- The files are wavetables in mono 32-bit float WAV (44.1 kHz, 2048-sample waves, 256 at most: the manual editor adds no wave to a table of 256), most of them with a mark (the `clm ` chunk, `<!>2048 10000000 …`: the samples of a frame, then flags). A mark whose first flag is not 0 is a morph: the table plays expanded to 256 frames by crossfades, whatever that flag: frame j of N at round(j·255/(N−1)), between two the next one weighs (i + 1)/(s + 1) at i frames into a span of s (`wavetable-frames.ts`, checked against `dsp/measurements/frames.json`; the second flag changes nothing it plays). `synth/services/wav.ts` reads their samples and the mark from the bytes (`loadWavetable` gives `{ frames, morph }`); not `decodeAudioData`, which resamples to the context rate (at 48 kHz a 2048-sample slice is 1.09 cycles and a table has ~278 waves instead of 256).
- The wavetable editor (`synth/wave-table-editor/`) also builds tables from manual drawing or from an uploaded audio file. `synth/services/audio-file.ts` reads that file at its own rate, never at the context's: a WAV through `wav.ts`, other formats decoded by an `OfflineAudioContext` at 44.1 kHz (their rate is unknown before decoding).
